# 子 agent 批量计算架构——三轮实验总结（FINAL）

2026-09-15/16，两个 spike + 一个规模轮，从 demo 到工程化的完整验证。
证据链：`docs/evidence/{batch-subagent,shepherd-spike,scale-round}/`，
计划链：`docs/superpowers/plans/2026-09-1{5,6}-*.md`。

## 一、子 agent 方案的优势（全部有实测数字）

### 1. 上下文经济学：主会话成本与任务数解耦

| 形态 | 上下文成本 |
|---|---|
| 单任务 solo（基线） | 每任务 28–31k——**每任务重付全款**（skill 装载+协议+门禁） |
| 11 任务 fan-out（第一轮） | 每相位会话 44.5–75.3k，**边际成本 ≈2–5k/任务** |
| 50 任务全链（第三轮） | 接任会话 **105k** 完成 50 任务恢复+提交+结算+汇总 |

50 倍的任务量，主会话只涨了 2.4 倍。solo 形态下 50 任务意味着 ~1.4M tokens 的
重付或毁灭性压缩——这不是优化，是**能不能做**的区别。

### 2. 失败隔离与日志防倒灌（契约的 ≤10 行纪律）

- 20 份结构化裁决（制备/分诊/解读）**零编造、零拒收**；分诊工把 MB 级日志消化
  成 5 行×200 字符的证据再进主会话。
- 最硬的证据：V5 制备缺陷（同侧 H 0.276Å）失败后，分诊工给出 **job.log 行号级**
  取证与坐标级修复方案，重试 15 秒转绿——**失败处理的全过程没有一行原始日志
  进过主会话**。
- 分诊工还发现上游 bug（result.json 把输入错误误分类为 ts-step-limit）——
  判断力下沉到工人后，连质检都变成了副产品。

### 3. 唤醒驱动：等待零成本

- watch/producer 服务端轮询（零模型请求），终态通知驱动唤醒。
- 第一轮：9 份完成通知**并入单回合**；第三轮：**36 份通知仍是单回合**——
  收件箱批处理在 3.6 倍通知量下不退化。挂起的 agent 不花钱。

### 4. 角色化最小权限（引擎级强制）

- toolFilter 是硬边界：制备工的工具目录里**根本没有** mat_exec（"拒绝发生在
  工具调用引擎层面"）；分诊工只有只读 exec；分析师零 exec。三轮全程零越权。
- 牧羊人（continuable）管多波链：单链会话 38.9–49.5k 有界，波间可注入、可汇报、
  可冷恢复——链式工作的生命周期自治成立。

## 二、子 agent 方案的必要性（没有它会怎样）

1. **上下文墙**：不 fan-out，50 任务 ≈300k–1.4M 上下文，主 agent 在第 10 个任务
   就开始失焦（第三轮实测：连*撰写*10 份自含委托 prompt 都会耗尽单回合输出预算）。
2. **失败密集型工作流不可运维**：日志诊断、重试决策、多波门检都是"读大量非结构化
   文本+判断"——确定性代码做不了（判断），主 agent 直接做会毒化上下文（体量）。
   子 agent 是唯一同时满足两个约束的形态。
3. **并行与规模**：10 制备工并行、2 牧羊人并行跑链、批量通知单回合吸收——
   主 agent 串行做这些的墙钟不可接受。
4. **无人值守的前提**：第三轮的中断恢复证明，状态外置（manifest）+ 角色工人使
   "任何会话随时死、任何新会话可接任"成为常态——单体会话架构给不了这个性质。

## 三、工程化的必要性（每个工程件都对应一次实测事故）

demo 与工程的差距不在"能不能跑通"，在**第 N 次运行、出错时、被中断时**还剩下什么：

| 工程件 | 诞生的实测事故（若没有它会怎样） |
|---|---|
| manifest 外置清单 | 第三轮两次中断（重启+max-tokens 截断）零损失接任——状态在会话里的批次会全灭 |
| 层间契约（contracts） | 防日志倒灌与编造的**机器可执行**边界；"converged=false 而可用需 concerns"这类细粒度判定有校验面（F2 贴边收敛案例） |
| 预算闸（budget+hook） | SH3 牧羊人在自治中提交被闸当场拒绝并服从——没有闸，无人值守的自治=失控的配额账单 |
| 估算/实际两本账 | 估算 25.0 vs 实际 1.627 核时（6.51%）——计费口径可审计，误拒（SH3）可归因可修复 |
| toolFilter 角色挂载 | 三个 disabled 的默认值坑（skill-filesystem/tool-subagent/control）都是实测抓出来的；权限随角色走是爆炸半径控制 |
| 自愈扫描（stale） | M13 的 producer 死了、清单里留着 status:killed——没有扫描协议，接任者无从知道哪里的账不平 |
| 瘦委托红线 | max-tokens 截断事故：自含 prompt 不随规模扩展——写进协议才不会在下一次重演 |
| 用量折叠（fold-child-usage） | per-child usage 无 API 面——不补计量，成本核算永远缺一角 |
| 波内不结束回合纪律 | S7 负发现（settled 可续子的作业被 owner-disposed 清理）——机理不明就写协议，链会在随机时刻断 |

**工程化的本质**：把"这次碰巧成功"变成"每次可预期失败模式"。三轮里每次事故
（V5 制备缺陷、F2 注入未生效、max-tokens、SH3 误拒、M13 producer 死亡）都被
转化为契约条款、闸、扫描协议或 skill 纪律——**demo 展示能力，工程化把能力变成资产**。

## 四、诚实的边界（子 agent 不解决什么）

- **集群 I/O 吞吐**：exec-gate 串行是正确性约束，提交中位 46s——子 agent 不加速
  它（H2/K6）；200+ 任务需要并行提交面/分批经理，是新设计题。
- **宿主机理缺口**：jobs 不感知（S7）、per-child usage API、outputSchema 不可
  按次传——三条已列上游反馈，当前都以树外协议绕过。
- **prompt 规模红线**：委托的经济性靠瘦形态维持，不是免费的。

## 五、定案与数字总账

**架构定案**：无状态组合经理（每相位/接任全新会话+manifest 恢复）｜数据在清单
不在会话｜瘦委托｜判断力 fan-out 给一次性角色工人、多波链给 continuable 牧羊人｜
集群 I/O 集中串行｜一切提交过预算闸（估算计费+实际对账）。

- 假设 20 条：18 confirmed（2 优于假设）+ 2 partial + 1 负发现坐实
- 中断 5 种（重启×2/max-tokens/上游 400/会话死亡）：全部无损失恢复
- 集群：70 sbatch，实际 ≈2.7 核时，秒级作业，零配额浪费
- 代码：全树外，489 测试绿，宿主仓两日零改动
